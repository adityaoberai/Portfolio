# adityaoberai.com V3

Repository: `adityaoberai/Portfolio`

Create and work exclusively on a new branch:

```text
v3-world
```

Do not modify `main` directly.

## Goal

Build the third generation of my personal website.

V3 is not a visual refresh of the current editorial site. Treat it as a new product direction. You may reuse existing factual content, routes, data and useful infrastructure, but you are free to replace:

- the visual design
- component architecture
- homepage
- styling system
- routing assumptions
- static-only architecture
- deployment adapter
- content abstractions

Stay in the Svelte/SvelteKit ecosystem unless there is an exceptionally strong reason not to.

The core product idea is:

> **Come spend a minute in my world.**

The default experience should be an interactive virtual bedroom/studio representing my life.

Visitors should learn about me by moving around the space, inspecting objects, and discovering the things I build, write, photograph, collect, speak about and organize.

Alongside this, build a first-class alternate **Index mode** for users who want a conventional, fast, professional site.

# 1. World mode

Routes:

```text
/        default/preferred mode
/world   always opens World
/index   always opens Index
```

First-time visitors should default to World.

Persist the visitor's preferred mode. Prefer a cookie so SSR can render the correct mode without a client-side flash.

## Experience

World is a small virtual bedroom/studio.

Prefer a stylized low-poly 3D or 2.5D aesthetic.

Think:

- small RPG bedroom
- Animal Crossing-style readability
- indie-game diorama
- warm personal studio

Do not make it:

- photorealistic
- cyberpunk
- RGB gamer-room aesthetic
- terminal/hacker themed
- generic developer-bedroom template

The room should feel specifically like **Aditya's room**.

# 2. Character

Prototype a movable stylized Aditya character.

The character acts as an expressive navigation cursor. The visitor is not role-playing or making decisions as Aditya.

## Desktop

Support:

- WASD
- arrow keys
- click-to-move
- clicking a major object may automatically walk the character toward it

Movement should be deliberately quick because the room is small.

Crossing the entire room should take only a couple of seconds.

Interactions should be forgiving. Do not require the player to:

- face the exact correct direction
- occupy a precise tile
- navigate around furniture carefully

Use generous interaction radii.

## Mobile

Prioritize:

- tap-to-move
- tapping objects directly
- large touch targets
- portrait usability

Do not require a permanent joystick unless real-device testing demonstrates that it improves the experience.

Landscape can be enhanced but must never be required.

Desktop and mobile should use the **same room**, not completely different experiences.

---

# 3. Camera

Use a controlled three-quarter/isometric perspective.

The visitor should understand most of the room immediately.

Do not require free camera orbiting.

When interacting with an object, the camera may:

- push in
- slightly reframe
- focus on that area
- dim or soften the rest of the room

Returning to the room overview should always be obvious.

# 8. Shared content model

World and Index must use the same content sources.

Do not create two manually maintained sites.

Move toward an artifact-oriented model.

For example:

```ts
export type ArtifactType =
	| 'project'
	| 'work'
	| 'essay'
	| 'photo'
	| 'collectible'
	| 'talk'
	| 'community'
	| 'note';

export type World = 'build' | 'write' | 'gather' | 'speak' | 'photograph' | 'collect' | 'personal';

export interface Artifact {
	id: string;
	type: ArtifactType;
	worlds: World[];
	title: string;
	description?: string;
	date?: string;
	image?: string;
	href?: string;
	externalUrl?: string;
	featured?: boolean;
}
```

An artifact may belong to multiple worlds.

For example:

```text
Writers' Room
→ gather + write + photograph

RenderATL talk
→ speak + build + write

Conference photograph
→ photograph + gather + work
```

Reuse existing TypeScript data where useful.

Do not introduce a database unless there is an actual requirement for one.

# 10. 3D implementation

Before selecting the rendering layer, research the current best Svelte 5-compatible options.

Threlte / Three.js is an obvious candidate, but evaluate:

- current Svelte 5 compatibility
- maintainability
- bundle size
- mobile performance
- ergonomics
- ecosystem maturity

Document the decision.

Do not overengineer the scene engine.

This is one small room, not a general-purpose game.

---

# 11. Performance

Treat performance as one of the main engineering constraints.

Prioritize:

- compressed GLB assets
- aggressively optimized geometry
- compressed textures
- sensible texture resolution
- instancing/reuse where useful
- lazy loading
- code splitting
- DPR caps
- device quality tiers
- minimal continuous animation
- sleep/reduced rendering when idle/backgrounded
- mobile thermal/GPU behaviour
- caching

The site must feel reasonable on a modern mid-range smartphone.

Do not optimize only for desktop gaming hardware.

---

# 12. Loading and fallback

Never present a blank WebGL canvas.

SSR a useful shell containing:

```text
Aditya Oberai

Come spend a minute in my world.

[loading state]

World / Index
```

If WebGL fails or is unsupported, offer Index immediately.

Index should never depend on loading the 3D scene.

# 13. Accessibility

World is allowed to be experimental, but content cannot become inaccessible.

Requirements:

- conventional routes
- Index mode
- keyboard support
- reduced-motion support
- meaningful labels for interactive objects
- semantic DOM UI around scene controls
- no information available only on hover
- visible focus states
- accessible fallback if the scene cannot run

Reduced-motion mode should substantially reduce:

- camera travel
- parallax
- exaggerated scene animation

without removing content.

# First milestone acceptance criteria

Do not treat “the room renders” as success.

The first milestone is done when:

1. `/world` loads a recognizable room.
2. A character can move comfortably on desktop.
3. Tap-to-move works sensibly on mobile.
4. Clicking/tapping major objects can move the character toward them.
5. At least four objects are meaningfully inspectable.
6. The room already communicates multiple sides of my personality.
7. World → Index is obvious at all times.
8. `/index` does not require the scene bundle.
9. Reduced-motion behaviour exists.
10. The experience performs acceptably on a real mid-range phone.
11. `main` has not been modified by V3 development.

---

# Important working style

Do not attempt the whole V3 implementation in one enormous change.

Start with the technical spike and vertical slice.

Temporary low-poly assets are acceptable.

Separate these questions:

1. Does the interaction model work?
2. Is the architecture sustainable?
3. Is the visual direction right?

Only invest heavily in final 3D assets after all three are answered positively.

When choosing between cleverness and usability, remember the product thesis:

> **Come spend a minute in my world.**

The visitor should remember the site because they understood me better, not simply because it used 3D.

## Renderer decision / researched 2026-09-30

| Option                  | Assessment                                                                                                                                                                                                                                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Threlte 8.6.1 + Three   | Current peers explicitly support Svelte >=5 and Three >=0.172. Declarative scene composition and lifecycle helpers are attractive for expansion. Core's on-demand rendering avoids idle GPU draws, but its scheduler retains an animation loop. Pointer interactivity additionally needs extras or direct raycasting. |
| Direct Three.js 0.186.1 | Selected for this bounded spike. Named imports, one scene module, explicit disposal, direct raycasting, and a requestAnimationFrame loop that stops completely at rest. Svelte owns all semantic UI. More lifecycle code is our responsibility.                                                                       |
| CSS/SVG 2.5D            | Cheap and accessible, but a movement/occlusion model would be custom, with weaker path to the requested low-poly 3D room. Keep conventional DOM as the fallback instead.                                                                                                                                              |

This is one room, not an engine. Renderer dependencies are loaded only inside
World's client mount. Geometry and materials are reused. Index never imports
the scene, even indirectly. Revisit Threlte if scene composition becomes the
dominant maintenance cost; the artifact data and DOM shell are independent.

Primary sources:

- https://registry.npmjs.org/@threlte/core/8.6.1
- https://threlte.xyz/docs/reference/core/canvas/
- https://threlte.xyz/docs/reference/core/use-task/
- https://github.com/threlte/threlte/blob/main/packages/core/src/lib/context/fragments/renderer.svelte.ts
- https://threejs.org/manual/en/rendering-on-demand.html
- https://threejs.org/manual/en/cleanup.html
- https://threejs.org/docs/#api/en/renderers/WebGLRenderer

Registry package size is not browser transfer size. Record actual production
chunks during verification. Three WebGLRenderer requires WebGL2; missing or lost
contexts must reveal a DOM fallback and a direct Index link.

## Deployment decision

Use **adapter-node 5.5.7** for a portable Node runtime (Node 24 is used locally).
The first attempt retained adapter-static, but production browser testing found
that `/index` resolved to the existing homepage's `/index.html`. A directory
output and explicit prerender entry fixed the build but not generic static
request routing. This exposed a real reason to establish the hybrid runtime now.

`/world` and `/index` SSR their useful HTML. Existing V2 homepage and deep pages
continue to prerender. There is no database or per-visitor content state yet.
The new adapter's route-aware handler correctly distinguishes `/` and `/index`.
Tests and `npm run preview` use the actual built Node server, not a static file
server that guesses HTML filenames.

Deployment implications: `npm run build`, then `npm start` (`node build`). Deploy
`build/`, package.json, package-lock.json and production dependencies to a Node
host; this output cannot replace a static-host upload. Set `HOST`, `PORT`, and
an explicit `ORIGIN` for the deployed URL. Do not trust proxy headers unless
the host's reverse-proxy contract is configured. The final host remains open:
Appwrite Sites, Cloudflare, or Vercel may require their supported adapter/config.
Appwrite Sites supports SvelteKit with SSR rendering, and path redirects there
are framework-level (application code), not platform config. That matches the
runtime redirect routes above. Which adapter Sites expects must be confirmed with
a real preview deployment before relying on it.
No account, DNS, public deployment, or existing production setting is changed.
References: https://svelte.dev/docs/kit/adapter-node,
https://appwrite.io/docs/products/sites/migrations/vercel

Phase 2 can use this runtime to SSR the preference cookie at `/` (which must then
stop prerendering). Explicit `/world` and `/index` routes must win over that cookie, then set
the chosen preference. Prerender factual deep pages where sensible. A static
host cannot implement this SSR behavior, so do not pretend localStorage solves
the no-flash requirement. Validate the final host-specific runtime before moving
the default homepage. Preserve the existing domain and social card
through the spike; migrate canonical metadata to adityaoberai.com at launch.

## Performance and input contract

- One controlled orthographic camera; no orbit, camera flight, physics, shadows,
  postprocessing, texture downloads, or perpetual decorative animations.
- DPR cap 1.25 for coarse pointers, 1.5 otherwise; a 1.0 low-quality option.
- Target <150 draw calls, <15k triangles, and <200 KB gzip lazy scene JavaScript.
  Budgets are provisional and must be checked against measured output.
- Only schedule frames for movement, resize, input, or state changes. Stop on
  hidden tab, loss of focus, and teardown. Clamp long frame deltas.
- Future models: shared/instanced meshes, optimized GLB, compressed textures at
  modest resolution, and independent lazy downloads. Add these only when assets
  actually require them.
- Keyboard movement is scoped to a focused room. Screen-relative WASD/arrows,
  normalized diagonals, clamped floor bounds, fast traversal, generous desk reach.
- Tap/click the floor to walk; desk interaction auto-walks to a safe approach.
  No tight furniture collision. DOM desk button offers the same interaction.
- Reduced motion disables gait bounce and makes point-to-point moves immediate.
- Native dialog handles focus containment and Escape. Closing returns focus.

## Real-phone gate (not yet passed)

Use the dev server's LAN URL on the same Wi-Fi. Keep access on a trusted network;
no firewall, tunnel, or public deployment changes are required by this spike.

Record device, OS, browser, connection, DPR setting, warm/cold load, and measured
frame time while moving. Check on a modern mid-range physical phone:

1. Portrait: entire room is legible, controls are at least 44px, no horizontal scroll.
2. Tap several floor points, then desk; character reaches them quickly and reliably.
3. Open/close the work dialog; scroll its content; Index is always reachable.
4. Rotate and return to portrait; room fits without stretching or disappearing.
5. Try low quality, reduced motion, background/resume, and five minutes of use.
6. Check no persistent idle rendering, stalls, or excessive heat. Target p95 moving
   frame time <=33ms (30fps); record real results rather than inferring from desktop.
7. Test WebGL2 disabled/context loss and a failed scene load; Index stays usable.

Desktop automation or resized screenshots are useful checks, not a substitute
for this gate. Do not mark first milestone acceptance #10 complete without it.
